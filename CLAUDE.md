## Project

SyncedList is a Flutter app (Dart package name `shopping_list`) for shared shopping lists that sync in real time through Firebase (Auth, Firestore, Crashlytics, Hosting). Targets Android (`ua.ovi.shared_shopping_list`), iOS (`ua.ovi.sharedshoppinglist`) and web. Built with Flutter 3.50 / Dart 3.14 (`sdk: ^3.14.0`). Widgets import `package:material_ui/material_ui.dart` / `package:cupertino_ui/cupertino_ui.dart` (the standalone Material/Cupertino packages), not `package:flutter/material.dart`.

## Commands

```bash
flutter pub get
flutter run                      # pick device with -d <id>
flutter analyze                  # lints: package:flutter_lints/flutter.yaml
flutter test                     # all tests
flutter test test/widget_test.dart --plain-name "<test name>"   # single test
flutter build apk / flutter build ios
```

Localization code generation (also runs automatically on `pub get`/build, since `generate: true`):

```bash
flutter gen-l10n
```

Android builds need JDK 17+ (`JAVA_HOME`). The Gradle build is Kotlin DSL (`android/*.gradle.kts`) with built-in Kotlin (`android.builtInKotlin=true`): don't apply the Kotlin Gradle Plugin, and avoid plugins that still do (they break the build in future Flutter versions); release signing reads the gitignored `android/key.properties` (`storeFile` absolute or relative to `android/`, `storePassword`, `keyAlias`, `keyPassword`); without it or the keystore it points to, it signs with the debug key.

Firebase Hosting (site `syncedlist`, https://syncedlist.web.app) serves the Flutter web build. `firebase.json` at the repo root publishes `build/web`, runs `flutter build web --release` as a predeploy step, and rewrites every path to `index.html`, so `/link` invites open the web app. Static files that ship with it (`terms.html`, `privacy.html`, and the `/.well-known` App Links / Universal Links files) live in `web/`, which Flutter copies into the build. `cleanUrls` serves them as `/terms` and `/privacy`; they share `web/legal.css`. Deploy from the repo root with `firebase deploy --only hosting`. The web app is an installable PWA (`web/manifest.json`) that works offline: `web/sw.js` is our own service worker (network first for the site's files, cache first for CanvasKit, the Firebase JS SDK and fonts on Google's CDNs), registered from `index.html`, which also hands it the URLs loaded before it took over. The custom `web/flutter_bootstrap.js` leaves out `serviceWorkerSettings`, because Flutter's deprecated `flutter_service_worker.js` only unregisters itself and would replace `sw.js`. On the web, `main()` turns on Firestore's IndexedDB cache (`persistenceEnabled`), which mobile has by default. `LegalLinks` (login screen and account sheet, every platform) opens the in-app `/terms` and `/privacy` routes (`lib/ui/legal/`), whose text lives in `legal_content.dart` with one `docs/legal_<lang>.dart` part per app language. The English text duplicates the HTML pages (kept because store reviewers and crawlers can't read Flutter's canvas), so change both together and bring every translation along; on the web, `AndroidAppLink` links to Google Play.

Cloud Functions (push notifications) live in `functions/`: `npm --prefix functions install`, `npm --prefix functions test`, deploy with `firebase deploy --only functions`.

Tests in `test/` cover only Firebase-free code (share links, translations, and the push UI with a fake `PushRepo` registered in get_it). Testing `App` itself would need Firebase mocked.

## Architecture

Layering: **UI widgets → async_redux actions → repos → data sources (Firestore / FirebaseAuth / SharedPreferences)**.

- **State management: async_redux.** A single global `mainStore` (`lib/main.dart`) holds an immutable `AppState` (`lib/state/`). State classes use hand-written `copyWith`/`==`/`toMap` inside `//<editor-fold desc="Data Methods">` blocks; keep these in sync when adding fields.
- **One action per file.** Each `ReduxAction<AppState>` sits in an `actions/` folder next to the screen that uses it (e.g. `lib/ui/list/items_list/actions/item_list_action_done.dart`). Business logic lives in `reduce()`; actions call repos directly. Some file names don't match the class inside (files under `ui/list/user_list/actions/` are named `new_list_action_*` but define `UserListAction*` classes).
- **Widgets** use the `StoreConnector` + private `_ViewModel.fromStore` pattern, and subscribe/unsubscribe to Firestore streams through `onInit`/`onDispose` dispatching `*Subscribe`/`*Unsubscribe` actions. Some widgets call `mainStore.dispatch(...)` directly.
- **Dependency injection: get_it.** All data sources and repos are registered as singletons in `setupDependencies()` in `main.dart`; repos and actions resolve them with `GetIt.I.get<T>()`. New repos and sources must be registered there.
- **Realtime sync.** `ListsRepo` and `ItemsListRepo` keep a single `StreamSubscription` and pass snapshots to a callback, which dispatches a "changed" action into the store. Mutating actions (done, reorder, delete) update local state optimistically *and* write to Firestore; the snapshot listener then reconciles. Note that `ItemsListRepo` is defined in `lib/data/repos/user_lists_repo.dart`.
- **Firestore schema** (`lib/data/sources/list/`):
  - `lists/{listId}`: `{id, name, order, members: [uid...]}`. A user's lists are queried with `members arrayContains uid`. Deleting removes the user from `members`, and the doc is deleted only when no members remain.
  - `items/{listId}/products/{itemId}`: `{id, value, order, done}`.
  - Reordering is a batched update of the `order` field.
- **Navigation** uses named routes in `lib/app.dart` (`/`, `/login`, `/main`, `/items`), driven from actions through `NavigateAction` with the global `navigatorKey`. `/items` receives the `UserList` as route arguments. The splash screen dispatches `CheckLoginAction`, which routes to `/login` or `/main`.
- **Auth** (`lib/ui/auth/actions/`): Google, Facebook and anonymous login all extend `BaseLogin`, which turns errors into `UserException` (shown by the app-wide `UserExceptionDialog`) and treats `LoginCancelled` as a no-op. On the web, Google sign-in uses `FirebaseAuth.signInWithPopup`, because google_sign_in 7 has no `authenticate()` there. On Android, the signing key's SHA-1 must be registered on the Firebase Android app, or Google rejects the sign-in.
- **Account** (`lib/ui/account/`): `main()` listens to `AuthRepo.accountChanges()` (Firebase `userChanges`) and stores the user in `LoginState.account`. The avatar button on the lists screen opens `AccountSheet`: guests (anonymous users) get Google/Facebook sign-in, signed-in users get Sign out, and everyone gets the theme picker. Guest sign-in (`AccountActionLink`) links the provider to the anonymous account so its uid and lists stay. If the provider already has an account, that account is signed in instead and the guest's lists, read from Firestore beforehand, are added to it; a list that fails to move is saved as a pending invite so `NewListActionAddFromInvite` retries it. Never sign a guest out or switch accounts without bringing their lists along.
- **Sharing / invites.** `Deeplink.createLink` builds `https://syncedlist.web.app/link?id=&name=`, opened in the app through Android App Links / iOS Universal Links (Firebase Dynamic Links was shut down). `initDeepLinks()` in `app.dart` (called from `main`) listens via `app_links` and dispatches `NewListActionFromDeepLink`, which saves the invite to SharedPreferences (`InviteRepos`). If the user is logged in it adds them as a list member right away; otherwise it sets the `loginToViewList` `Event` so the login screen can prompt.
- **Push notifications** (shared lists only). Cloud Functions in `functions/` (TypeScript, Node 22; pure logic in `src/batch.ts` and `src/texts.ts`, tested by `npm test`). `onItemWritten` (a Firestore trigger with auth context, so a deleted item can be credited to whoever removed it) records each add, check-off and removal in `notifications/{listId}` (`pending`) and, on the first change of a quiet list, queues the `sendListUpdates` task for 10 s later (fixed window, `WINDOW_SECONDS`). That task folds the batch into each member's running total (`unseen.{uid}`, minus their own changes) and pushes it with the list id as Android `tag`/`collapseKey`, iOS `apns-collapse-id` and web `tag`, so a push replaces the previous one for the same list only. Item writes carry `updatedBy: uid` (`DbItemsStore`), which wins over the trigger's `authId`; writes with neither (server or console edits) don't notify. An item added and removed before the member saw it cancels out. Opening a list clears the user's total (`PushActionMarkSeen`). The app (`lib/ui/push/`) keeps the permission in `AppState.pushPermission` (`PushPermission`). On mobile it asks once the user has a shared list (`PushActionEnable`); on the web it never asks on its own, because Safari and Firefox only show the prompt from a tap: `PushBanner` above the lists (shared lists only, until "Not now", saved as `pushBannerDismissed`) and `NotificationsSection` in the account sheet ask with `PushActionEnable(fromTap: true)`. Every visit to a shared list shows `ListPushPrompt` until this device gets notifications ("Turn on", how to unblock them, or the iPhone Home Screen hint; "Not now" / "Ok" hide it for that visit); it re-checks the permission on open and on app resume, all three sharing `PushPromptCard`, and the section also explains a blocked permission or, in iPhone browsers, adding the app to the Home Screen. It saves this install's FID (firebase_messaging's `register()`/`onRegistered`) to `users/{uid}/devices/{fid}` with its locale, moves it on account changes and deletes it on sign-out (`PushRepo`), registering again on every app start. When FCM rejects a device as unregistered, `sendListUpdates` marks its doc `unregisteredAt` and skips it; on its next start the app sees the mark, resets its Firebase Installation (`firebase_app_installations`) and registers a new FID, because the web SDK otherwise reuses its cached registration for up to 7 days. A tapped push opens the list via `PushActionOpenList` (held in `PushRepo.pendingListId` until the splash screen has signed in); on the web, `web/firebase-messaging-sw.js` (separate from `sw.js`, at the SDK's own scope) shows pushes and opens `/?openList=<id>` or messages an open tab, which `index.html` reloads at that URL. `ItemListActionUnsubscribe` takes the screen's `UserList` so a list screen replaced by another doesn't cancel the new one's subscription. Deploy with `firebase deploy --only functions` (Blaze plan; Cloud Tasks API). iOS needs an APNs key uploaded in the Firebase console.
- **Localization** uses Flutter gen-l10n: edit `lib/l10n/app_en.arb` (template) and the other `app_<lang>.arb` files (uk, ru, pl, de, es, pt (Brazilian), fr, it, tr, cs, ja, id, hi). A new language also needs its legal docs part, push strings in `functions/src/texts.ts` and an entry in `CFBundleLocalizations` (`ios/Runner/Info.plist`); `lib/l10n/app_localizations*.dart` are generated, so don't edit them by hand. Access strings with `AppLocalizations.of(context)`. `MaterialApp` must use `appLocalizationsDelegates` from `lib/localization.dart`, not the generated `AppLocalizations.localizationsDelegates`: the generated list's Material delegates come from `flutter_localizations`, which `material_ui`'s `MaterialApp` doesn't recognize, so every non-English language fails.
- **Theming** (`lib/ui/theme/app_theme.dart`): Material 3 light and dark `ThemeData` built with `ColorScheme.fromSeed` from the brand orange (`DynamicSchemeVariant.fidelity` keeps it close to the seed). Use `Theme.of(context).colorScheme` roles, never hardcoded colors, so both themes work. The user's System/Light/Dark choice is `AppState.themeMode` (`AppThemeMode`), saved by `ThemeRepo`, loaded in `main()` before `runApp`, and changed in the account sheet.
- **Lists** use Material's `ReorderableListView` with `onReorderItem` (it gives the final index the reorder actions expect) and `DragHandle` / `liftedProxyDecorator` from `lib/ui/widgets/reorderable.dart`. Shared bits like `EmptyState`, `AppMark` and `menuAction` are in `lib/ui/widgets/widgets.dart`.
- **Item suggestions** (`SuggestionsRepo`, `lib/data/repos/suggestions_repo.dart`): the add-item dialog shows chips of names from a device-local history (SharedPreferences `itemHistory`, at most 300). `NewItemActionAddList` counts what the user adds, `ItemListActionChangeList` stores names seen in lists (count 0), and sign-out clears it. `suggestItems` ranks prefix matches, then word starts, then substrings, most used first, and leaves out items still to buy. A tapped chip adds the item right away; editing an item shows none.
- **Item sort preference** (`SortRepo`) is stored in SharedPreferences as a JSON array of `ItemSort` names.
- Errors are reported to Crashlytics through `runZonedGuarded` and `FlutterError.onError` in `main()`.
